# Private staging export handoff

No production SQL, new login roles, permission changes, branch creation or release is authorised. Use an EXISTING authorised login on a trusted owner-controlled machine. This handoff is schema-only; no customer/auth user data or role passwords is requested.

## Minimum owner steps

1. Install PostgreSQL **17** client tools: `psql`, `pg_dump`, `pg_dumpall`; put their PostgreSQL 17 bin directory first on PATH. Also require Bash, `cmp`, `mktemp`, `chmod` and `sha256sum` (GNU coreutils on macOS). Check each PostgreSQL tool with `--version`; the script refuses another major. Source was PostgreSQL17.6; server compatibility is rechecked at restoration, not inferred from client installation.
2. Configure libpq locally using the existing connection. Set `PGHOST` and `PGUSER` explicitly for the source guard; set `PGPORT` if non-default. Direct host is `db.tbafuqwruefgkbyxrxyb.supabase.co`. An existing session pooler may be used with its actual owner-authorised port and project-qualified user; do not use transaction pooling for this export. A named `PGSERVICE` can provide local configuration, but PGHOST/PGUSER must still be explicit and consistent. The script fixes database `postgres`, TLS required and read-only sessions.
3. Supply authentication through a local `PGPASSFILE`/`~/.pgpass` (0600, matching host/port/database/user) or an approved local secret-store environment injection. Do not put passwords in shell arguments, source files, chat, terminal recordings or Git. Avoid `set -x`. An API access token is not a PostgreSQL password. All commands use `--no-password`; no prompt, Supabase link or automatic role provisioning occurs.
4. From the checkout run `bash scripts/export-vinetrack-review-schema.sh`. Only the script and companion `scripts/vinetrack-review-catalog.sql` need be obtained from Git. Successful artifacts appear in a private0700 `/tmp/vinetrack-schema-private.*` directory, files restricted by077umask: `schema.sql`, `roles-password-free.sql`, source catalogs and `SHA256SUMS`. Transfer the complete directory via the organisation's encrypted private file-transfer channel to the authorised staging operator; in the received directory run `sha256sum -c SHA256SUMS` before use (checksum filenames are relative and travel with the directory). Never attach these exports to chat or commit them. `/tmp` may be automatically cleared: retain an owner-controlled encrypted private copy outside every repository before transfer.

If export fails, STOP. Keep stderr privately and report only the command stage, SQLSTATE if supplied, exact denied schema/object/catalog and missing privilege (sanitise credentials/connection strings). A successful partial schema dump is NOT acceptable. No existing connection is configured in this sandbox, so no specific privilege denial has been observed yet.

Typical failures must be distinguished: CONNECT on postgres; USAGE/catalog access for a named schema; SELECT required by a dump's relation/sequence inspection or locking; access to role attributes/membership/settings catalogs used by `pg_dumpall --no-role-passwords`; or ownership required for a particular protected managed object. Report the ACTUAL server diagnostic, not a guessed request for superuser/CREATEROLE. `--no-role-passwords` avoids password-hash extraction but does not guarantee every other catalog privilege. Do not request blanket elevation or change production grants; the owner can select another already-authorised trusted connection. Native-auth/managed objects cannot be silently excluded to make a partial export pass.

## Required staging-operator review (not automatic restore)

**`roles-password-free.sql` contains Supabase-managed roles as well as custom roles. It is an inventory/review artifact, NOT a script to replay wholesale.** Do not pipe it into psql.

- Provision/use only an owner-approved isolated PostgreSQL17/Supabase-compatible target. Cost-bearing creation needs explicit approval. No production endpoint fallback, copied credentials, live webhooks, active schedules, vault secrets or customer rows.
- Capture the target's native system roles, role attributes/memberships, installed auth/storage schemas and extensions FIRST. Native Supabase roles such as anon, authenticated, service_role, authenticator, postgres and supabase_* must remain compatible with the target's managed platform. Do not CREATE/ALTER them from the source dump or overwrite their passwords, SUPERUSER/BYPASSRLS/login attributes or internal memberships. Name prefixes alone are not a reliable custom-role classifier.
- Build a private, manually reviewed dependency allowlist from source object owners, ACLs, default privileges, policy roles, SECURITY DEFINER owners and role memberships. For each role, record source/target mapping, purpose, attributes, required memberships and approved grants. Restore only genuinely missing required custom roles and reviewed grants. No production credential is reused. A dependency that cannot be reproduced safely blocks restoration; it is not omitted.
- Keep the full schema artifact immutable as source evidence. Restore into the compatible empty target only through a reviewed restore plan that reconciles already-present managed auth/storage/extension objects. Inspect schema-embedded owners, ACLs, default privileges, functions, publications, network-capable definitions and schedules too; selective roles alone does not make whole schema replay safe. Preserve RLS/trigger/function definitions and record every platform-specific mapping/exclusion with justification. Do not use `--no-owner`/`--no-acl` as an unexplained way to force success.
- Compare restored schemas, object definitions/hashes, roles/memberships/ownership, privileges, RLS, constraints, indexes, extensions/versions, native auth and triggers to the private source catalog BEFORE SQLv2. Explicitly reconcile platform-managed differences; unresolved application-contract differences fail acceptance. A schema-only dump does not restore external Storage label binaries, extension installation packages or approval rows. Use synthetic hashed label documents and synthetic reviewed product/application evidence for admission fixtures.
- Then execute SQLv2 storage validation separately from installation/testing of reviewed server admission. Actor-native-auth/RLS/manual/history/old-client and direct/RPC/Trip/tank zero-side-effect acceptance is still required. Client unit tests do not substitute for these tests.
